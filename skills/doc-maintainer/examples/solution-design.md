## 1. Project Purpose

### What It Does

taskflow is a lightweight web application for managing personal and team task lists. Users can create projects, assign tasks to team members, set due dates, and track progress through a kanban-style board. The application sends email reminders for overdue tasks and supports export to CSV.

### Who It's For

Small teams (2–20 people) who want simple shared task tracking without the overhead of enterprise project management tools. The primary user is a team lead or individual contributor managing a backlog of work.

### Problem It Solves

Before taskflow, teams relied on shared spreadsheets or ad-hoc chat threads to track work, leading to tasks falling through the cracks and no single source of truth for project status. taskflow provides a persistent, structured record of all tasks and their state.

### Non-Goals

- Not a time-tracking tool — taskflow records what work needs to be done, not how long it took.
- Not a real-time collaboration tool — it does not support simultaneous editing or live presence indicators.
- Not a billing or invoicing system.

## 2. Solution Architecture

### System Overview

taskflow is a traditional three-tier web application: a React single-page application running in the browser, an Express REST API server, and a PostgreSQL database. The API server is stateless; authentication is handled via short-lived JWTs. A separate background worker process handles email notifications by polling a `notifications` queue table in the database.

| --------- | ---------- | ---- |
| `ui` | React 18, Vite, Tailwind CSS | Browser SPA — task board, project sidebar, settings |
| `api` | Node.js 20, Express 5 | REST API server — handles all CRUD operations |

| `nginx` | Nginx 1.25 | Reverse proxy and static asset server |

### Data Flow

1. **Authentication**: User submits email + password → `POST /auth/login` → API validates credentials, issues a 15-min JWT and a 7-day refresh token stored as an httpOnly cookie → subsequent API requests send JWT as `Authorization: Bearer <token>`.
2. **Task creation**: User fills form in UI → `POST /api/tasks` with project ID, title, assignee, due date → API persists to `tasks` table → response includes the new task ID → UI adds the card to the board optimistically.
3. **Overdue notifications**: Email worker polls `notifications` table every 5 minutes → for each pending row, calls SendGrid API → on success, marks row as `sent`; on failure, increments `retry_count` (max 3) → if retry_count exceeds limit, marks as `failed` and logs.
4. **Export**: User clicks "Export CSV" → `GET /api/projects/:id/export` → API streams CSV rows directly from DB query → browser triggers download.

### External Integrations

| Integration | Type | Purpose |
| ----------- | ---- | ------- |
| SendGrid | REST API (HTTP) | Transactional email delivery for overdue task reminders |

### Infrastructure & Deployment

taskflow is containerised with Docker Compose (three services: `api`, `worker`, `db`). In production it runs on a single DigitalOcean Droplet with Nginx terminating HTTPS via Let's Encrypt. CI is GitHub Actions: lint → test → build Docker image → push to GHCR → deploy via SSH.

## 4. Key Architectural Decisions

- **Single database for both API and worker**: The email worker reads the `notifications` table directly rather than using a message broker. This avoids operational complexity at the cost of tight coupling to PostgreSQL; acceptable at current scale.
- **Stateless API with JWT**: No server-side session store. JWTs are short-lived (15 min) with a rotating refresh token cookie. Chosen to simplify horizontal scaling, accepting that token revocation before expiry is not possible without a denylist.
- **Polling worker instead of event-driven**: The notification worker polls rather than using PostgreSQL LISTEN/NOTIFY or a message queue. Simpler to operate and debug; acceptable given the 5-minute notification latency is within spec.
- **No soft deletes**: Tasks and projects are hard-deleted. Audit requirements were explicitly out of scope at launch; the schema does not include `deleted_at` columns, making future addition a migration effort.
- **CSV export via streaming query**: Export avoids loading all rows into memory by streaming from the database query directly to the HTTP response. Avoids OOM issues on large projects.
