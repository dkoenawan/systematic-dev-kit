# Tasks

## What Is Tasks?

A Task is the central unit of work in taskflow. It represents a discrete piece of work that needs to be done — assigned to a team member, associated with a project, and tracked through a defined lifecycle until it is completed or cancelled. Tasks are what users create, move between states, and get reminded about when overdue.

## How It Works

A Task is created when a user submits the "New Task" form in the UI, which calls `POST /api/tasks`. The API validates the project membership of the assignee, sets the initial state to `open`, and persists the row. The task then lives on the project board, visible to all project members.

State transitions are driven by user actions on the board: dragging a card from "To Do" to "In Progress" calls `PATCH /api/tasks/:id` with `{ status: "in_progress" }`. The service layer enforces valid transitions (e.g., a `cancelled` task cannot be moved to `done` directly). When a task's `due_date` passes without the status reaching `done` or `cancelled`, a background check (run at midnight UTC via the notifications worker) creates a row in the `notifications` table, which the email worker picks up and dispatches.

A task reaches a terminal state when it is marked `done` or `cancelled`. Terminal tasks remain in the database and are visible in the "Completed" filter. There is no soft delete — hard deletion is permanent and reserved for admin cleanup.

## Core Objects / Entities

| Object | Description |
| ------ | ----------- |
| `Task` | The primary entity. Fields: `id`, `title`, `description`, `status`, `priority`, `due_date`, `created_by`, `assigned_to`, `project_id`, `created_at`, `updated_at`. |
| `TaskStatus` | Enum: `open`, `in_progress`, `blocked`, `done`, `cancelled`. Defines valid lifecycle states. |
| `TaskPriority` | Enum: `low`, `medium`, `high`, `critical`. Controls sort order on the board. |

## Internal Architecture

Task state transitions are validated by an explicit transition table in `task.service.ts`:

```ts
const VALID_TRANSITIONS: Record<TaskStatus, TaskStatus[]> = {
  open:        ['in_progress', 'cancelled'],
  in_progress: ['blocked', 'done', 'cancelled'],
  blocked:     ['in_progress', 'cancelled'],
  done:        [],
  cancelled:   [],
};
```

Any PATCH request with a `status` value not in the allowed transitions for the current state returns a `422 Unprocessable Entity`. This prevents the UI from accidentally producing invalid state — the rule lives in the server, not the client.

## Dependencies

- **Internal**: `auth` — task routes require a valid JWT; `db` — all queries go through the shared connection pool; `notifications` — task service creates notification rows when a task becomes overdue.
- **External**: None directly. Tasks use only the shared PostgreSQL connection.

## Gotchas

- The `due_date` column stores a date (not a timestamp). Overdue detection runs at midnight UTC, meaning a task due on `2026-04-21` is not flagged until `2026-04-22 00:00 UTC`. Teams in UTC+12 may see notifications appear to arrive a day late from their perspective.
- Deleting a project cascades to delete all its tasks (`ON DELETE CASCADE` in the FK). There is no warning in the UI before project deletion. Backups are the only recovery path.
- `assigned_to` can be `NULL` — unassigned tasks are valid. The notification worker skips tasks with no assignee (no email to send to).
