# Feature Spec: Task Executor Skill

> Generated by /systematic-dev-kit:plan | Date: 2026-05-01 | Status: Draft
> Relates to: New skill in this plugin repo. Depends on: `/systematic-dev-kit:plan` (for design specs), aligns with: `/systematic-dev-kit:doc-maintainer` (cron + branch patterns).
> **Template note**: Standard plan template (DB/Backend/Frontend) doesn't fit a meta-skill. Adapted to State / Execution / Interface layers.

## Summary

A new skill `/systematic-dev-kit:task-executor` that runs large tasks autonomously via cron over multiple days. After an interactive planning conversation, it picks a GitHub issue, decomposes it into hour-sized tasks (using `/systematic-dev-kit:plan` internally), and executes up to 3 tasks per cron firing (every 6h by default). Each run: rebases on main, picks the next eligible task, executes, runs tests, commits with conventional-commit messages, ticks the checkbox. On full completion: opens a PR, comments on the issue, uninstalls the cron. The user maximizes token efficiency by offloading large work to off-hours runs.

## State Layer

### Persistent Artifacts

**Plan file**: `specs/<feature-name>/tasks.md` (sibling to `overview.md` produced by plan skill).

```yaml
---
issue: 42
branch: feat/user-roles
status: in-progress         # in-progress | complete | paused | failed
test_command: bun test      # null if none detected and user confirmed proceed-without
last_skill_commit: <sha>    # sha of most recent commit made by this skill; null at init
retry_counts:               # task-index → consecutive-fail count; reset to 0 on success
  3: 1
budget:
  max_tasks_per_run: 3
  max_wall_clock_minutes: 90
  stop_on_first_failure: true
schedule: "0 */6 * * *"     # cron expression, stored for reference
---
```

Body — checklist with three states and explicit dependencies:

```markdown
- [x] Add `User.role` field to Prisma schema
- [x] Generate and apply migration
- [ ] Implement `AssignRoleCommand` with validation (depends on: 2)
- [!] Wire up `/admin/users` route (failed 2026-05-01: tsc errors in adjacent file)
- [ ] Add role badge to user list (depends on: 4)
- [ ] Write integration test for role assignment (depends on: 3)
```

**Source-of-truth rule**: plan file is authoritative. Skill never reads back from git log or issue comments to decide what to do next.

### State Invariants

- Task index is 1-based line position within the checklist
- Status markers: `- [ ]` unchecked, `- [x]` complete, `- [!]` failed-and-skipped
- Failed marker line format: `- [!] <description> (failed YYYY-MM-DD: <reason>)`
- Dependencies: `(depends on: N)` or `(depends on: N, M)` — references task indices
- Branch name: `feat/<feature-name>` (kebab-case, derived from issue title at planning time)
- Commit format: conventional commits, scoped to feature (`feat(user-roles): add User.role field`)
- Idempotency: each run checks `last_skill_commit` against current HEAD; if HEAD has commits beyond it that aren't from the skill, concurrency-conflict path triggers

### Concurrency & Retry Rules

- Lockfile: `logs/task-executor/.lock` — second invocation exits silently if held
- Concurrency conflict (user committed to branch): retry next run; if still conflicted on second consecutive run, halt + issue comment, don't uninstall cron
- Task failure (test fail / can't proceed / no diff produced): leave `- [ ]`, bump `retry_counts[index]`, comment on issue. On second consecutive failure of same task: convert to `- [!]` with date+reason, skip going forward
- All-blocked state (every remaining `- [ ]` depends transitively on a `- [!]`): open **draft PR** with completed work, uninstall cron, comment on issue

## Execution Layer

### Daily Run Sequence (Mode: `execute`)

| Phase | Step | On Failure |
|---|---|---|
| 0. Git safety | Acquire lock; stash original branch ref; `git fetch origin`; checkout work branch; rebase on `origin/main` | Branch missing → halt + comment, don't uninstall. Rebase conflict → retry next run; second time → halt + comment |
| 1. Plan resolution | Find `specs/*/tasks.md` with `status: in-progress`. Verify exactly one. Verify `last_skill_commit == HEAD` ancestor | Multiple → halt + comment all linked issues. Mismatch → concurrency-conflict path |
| 2. Task selection | Walk checklist; first `- [ ]` whose deps all `- [x]`; budget-aware loop up to `max_tasks_per_run` | None eligible + some `- [!]` exist → all-blocked path (draft PR + uninstall). None eligible + all `- [x]` → completion path |
| 3. Execute (per task) | Read task description; execute in fresh-context conversation; run test command; on success tick box + conventional commit; on fail bump retry counter | Bump `retry_counts[index]`; if now ≥2 → mark `- [!]`. Stop the run (don't burn budget on dependents). Comment on issue with reason + test output tail |
| 4. Push & check completion | After loop ends: push branch. If all `- [ ]` now `- [x]`: set `status: complete`, open ready-PR via `gh pr create`, comment on issue, uninstall cron | `gh pr create` fails because PR exists → fetch PR URL, comment on issue, uninstall anyway (idempotent) |
| 5. Restore | Checkout original branch; release lock | Always runs (trap on exit) |

### Budget Enforcement

Per-run loop terminates on first hit of: `max_tasks_per_run` reached, `max_wall_clock_minutes` exceeded, first failure (if `stop_on_first_failure: true`), or no eligible task remains.

Budget is wall-clock + count, not token-based. Token introspection is unreliable mid-run; a 6-hour cron cadence aligning with the 5-hour Claude quota window mitigates quota exhaustion.

### Helper Scripts (14 single-purpose)

| Script | Purpose | I/O |
|---|---|---|
| `install-schedule.sh <repo> [--time HH:MM] [--every Nh]` | Register cron job. Preflight: `gh auth status`, scan crontab for clashing `claude` jobs | Stdout: confirmation + cron line |
| `uninstall-schedule.sh <repo>` | Remove cron job for this repo | Stdout: confirmation |
| `execute-daily.sh <repo>` | Cron entry point. Logs to `logs/task-executor/YYYY-MM-DD.log`. Invokes `claude` with skill in `execute` mode | (logs only) |
| `prepare-branch.sh <repo>` | Phase 0: stash, fetch, checkout work branch, rebase | Stdout: "ok" or `error:<reason>` |
| `find-active-plan.sh <repo>` | Locate `specs/*/tasks.md` with `status: in-progress` | Stdout: path or "none" or "multiple:<paths>" |
| `select-next-task.sh <plan-file>` | Parse checklist, apply dependency rules, return next eligible | JSON: `{index, text, retry_count}` or `{result: "none"}` or `{result: "all_blocked"}` |
| `mark-task.sh <plan-file> <index> <status> [reason]` | Tick `- [x]`, mark `- [!]` with date+reason, or update retry counter in frontmatter | Writes file in place |
| `commit-and-push.sh <repo> <commit-message>` | Stage tracked changes (incl. plan file), commit, push. Updates `last_skill_commit` in plan file | Stdout: sha or `error:<reason>` |
| `comment-on-issue.sh <issue-number> <message>` | Wraps `gh issue comment` | Stdout: confirmation |
| `open-pr.sh <repo> <issue-number> [--draft]` | Wraps `gh pr create`, links issue with `Closes #N` | Stdout: PR URL |
| `detect-test-command.sh <repo>` | Walk `package.json` scripts.test → `Makefile` test → `pyproject.toml` → `Cargo.toml` → `go.mod` | Stdout: command or "none" |
| `run-tests.sh <repo> <test-command>` | Run, capture exit code + tail of output | JSON: `{passed: bool, output_tail: str}` |
| `restore-branch.sh <repo>` | Checkout original branch (pre-stashed ref) | Stdout: confirmation |
| `check-idempotency.sh <repo>` | Has skill committed today? | Stdout: "ran_today" or "ok" |

### Failure Mode Matrix (E1–E14)

| # | Failure | Handling |
|---|---|---|
| E1 | Work branch missing | Halt + issue comment. Don't uninstall (user may recreate) |
| E2 | Rebase conflict on main | Retry next run; second time → halt + comment "manual rebase needed" |
| E3 | No active plan found | Uninstall cron, exit clean |
| E4 | Multiple in-progress plans | Halt + comment all linked issues, don't uninstall |
| E5 | All remaining tasks blocked by `- [!]` | Open **draft PR**, uninstall, comment on issue |
| E6 | Task execution itself fails (LLM stuck) | Same as test failure path: bump retry counter, comment, stop run |
| E7 | Tests fail | Bump retry counter; second time → `- [!]`; don't commit work changes; comment with test tail |
| E8 | Test command is null | Skip test step, log "tests skipped — no command configured" in commit body |
| E9 | Nothing to commit (empty diff) | Treat as task failure (no work happened); bump retry counter |
| E10 | Push rejected (force-pushed remote) | Halt + comment "remote diverged", don't uninstall |
| E11 | `gh` unauthenticated | Caught at `install-schedule.sh` preflight; refuse install. Mid-run: log to file, halt silently |
| E12 | `gh pr create` fails (PR exists) | Fetch existing PR URL, comment, uninstall anyway |
| E13 | Cron fires while previous run active | Lockfile in `logs/task-executor/.lock`; second invocation exits |
| E14 | Branch ahead of `last_skill_commit` (user committed) | Retry next run; second time → halt + comment |

## Interface Layer

### Invocation Modes

| Mode | Syntax | Purpose |
|---|---|---|
| Default | `/systematic-dev-kit:task-executor` | Auto-dispatch: no plan → enter `plan` mode (asks for issue number); plan exists → `status` |
| Plan | `/systematic-dev-kit:task-executor plan <issue-number>` | Interactive planning conversation; produces `tasks.md`, branch, cron |
| Execute | `/systematic-dev-kit:task-executor execute` | Cron entry only — runs daily sequence. Not for humans |
| Status | `/systematic-dev-kit:task-executor status` | Show active plan, task counts, retry counts, last commit, next eligible task, cron schedule |
| Stop | `/systematic-dev-kit:task-executor stop` | Uninstall cron, set status `paused`, comment on issue. Plan + branch preserved |
| Resume | `/systematic-dev-kit:task-executor resume` | Re-install cron for paused plan |

### Planning Conversation (Mode: `plan`)

Phases (in order):

1. **Preflight** — `gh auth status` ok, repo is git, issue exists, no other in-progress plan, no clash with existing crontab claude-jobs at the proposed time
2. **Issue ingest** — `gh issue view <N>` → title, body, labels. If body has existing `- [ ]` checklist, use as draft input
3. **Feature name derivation** — kebab-case from issue title; confirm with user; check `feat/<name>` branch availability locally + remotely
4. **Design spec resolution** — if `specs/<feature-name>/overview.md` doesn't exist, **invoke `/systematic-dev-kit:plan` internally** to produce it. The new file lives at `specs/<feature-name>/overview.md` (revised location — see Plan-Skill Adjustments below)
5. **Hour-sized decomposition** — read overview.md's Implementation Order, decompose into hour-sized tasks (≈ one focused commit each, ~30–90 min agent work). Auto-decompose with dependency annotations, present for approval
6. **Test command detection** — `detect-test-command.sh`; show what was found; user accepts or overrides; if none, prompt user to declare or proceed-without (stored as `null`)
7. **Schedule confirmation** — ask cron timing (default `0 */6 * * *` = every 6h). Surface clashing-cron warning if applicable
8. **Approval gate** — show summary (branch, plan file path, task count, test command, schedule), three options: "nails it / adjust / rethink"
9. **Commit** — write `specs/<feature-name>/tasks.md` with frontmatter, create branch, commit plan file, push, run `install-schedule.sh`, comment on issue: "automation started — runs every 6h"

### Plan-Skill Adjustments (Required Coupling Change)

The existing `/systematic-dev-kit:plan` writes to `specs/<feature-name>.md`. To support sibling-file layout:

- Plan skill's Phase 5 file output changes from `specs/<feature-name>.md` to `specs/<feature-name>/overview.md`
- Migration: existing `specs/*.md` files unaffected; only new specs use the directory layout
- Plan skill remains otherwise unchanged — no awareness of issues, branches, or execution

This is a **breaking path change** for plan, requiring a minor version bump on the plugin.

### State Layer ↔ Interface Layer Boundary

The skill is "thin orchestration": Claude reads plan files, calls scripts, makes commit-message + task-execution decisions. The 14 scripts handle all deterministic work (git, gh, cron, parsing). This minimizes per-run token usage — Claude doesn't construct git commands, doesn't shell-out raw, doesn't parse YAML by hand.

## Open Questions

1. **Mode-conditional model selection**: SKILL.md frontmatter is static — can't have one model for `plan` mode (Opus, judgment) and another for `execute` mode (Haiku, mechanical). Options: accept Opus for both (simpler, more tokens), or split into two skills (`task-executor-plan` + `task-executor-execute`) sharing scripts. Defer to implementation.

2. **Issue creation**: spec assumes issue exists before `plan <N>`. Should there also be a flow that creates an issue from the planning conversation if user doesn't have one yet? Out of scope for v1.

3. **Multi-repo**: cron runs per-repo. If user runs the skill in repo A and repo B, two separate crons. Acceptable for v1 — no shared state, no cross-repo orchestration.

4. **`run-now` mode**: explicitly excluded per Q10b. May reconsider if testing the cron flow proves painful.

5. **Existing-PR detection at planning**: if user runs `plan <N>` for an issue that already has an open PR, should we halt or proceed? Conservative default: halt with "PR #X already exists for this issue — close it or use a different issue." Not yet enumerated in failure matrix.
