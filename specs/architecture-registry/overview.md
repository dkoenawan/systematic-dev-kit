# Feature Spec: Architecture Registry & System Model

> Generated by /systematic-dev-kit:plan | Date: 2026-05-29 | Status: Draft v3
> Relates to: Full redesign — all skills + new /adr + new post-hook validator

---

## Summary

After months of real use, the kit's per-feature spec model breaks down at scale. The problem is not the specs — it's that there is nothing above them. Every new feature requires re-deriving what the whole system is. Agents duplicate constructs. Humans forget why decisions were made. The spec and the code drift apart silently.

This redesign introduces a **System Model** — a living construct registry that sits above the feature specs, is maintained by every skill, and answers the questions that currently have no answer:

- Does something that does X already exist before I build X?
- What does "auth" touch across the entire stack?
- Why was it built this way?
- Does what was built still match what was planned?

The System Model is not a docs folder. It is the externalised memory of a senior engineer: what exists, what it does, how it connects, why it was built that way, and whether it still matches the contract it was built against.

---

## The Core Problem (Precisely Stated)

Feature specs work. The failure mode is specific: **a construct gets built as part of a feature, and six months later nobody remembers it exists.** A utility class. A service. A helper. It lives in `src/utils/` or `src/services/` and the next agent or developer building a new feature creates a duplicate because they had no way to know it was there.

The solution is not more feature-level documentation. It is a **construct registry** — indexed by what things do, not where they live or which feature created them.

## Documentation Architecture: arc42 + C4 + Construct Registry

The System Model is structured using **arc42** as the documentation backbone, **C4** as the visual notation inside arc42's building block view, and the **Construct Registry** as the operational data layer. These three are complementary — not competing.

| Layer | Framework | What it answers |
|-------|-----------|----------------|
| Why / Goals / Strategy | arc42 §1, §2, §3, §4 | Why does this system exist? What constraints bind all decisions? What is the solution strategy? |
| What exists (static) | arc42 §5 + C4 diagrams | What building blocks exist? How are they composed? Black box → white box per level. |
| How it behaves (dynamic) | arc42 §6 + sequence diagrams | How do building blocks interact during key scenarios? |
| Where it runs | arc42 §7 + C4 deployment | What environments exist? Where does each building block run? |
| Cross-cutting rules | arc42 §8 | What patterns apply uniformly across all building blocks? (= patterns.md) |
| Why decisions were made | arc42 §9 | ADRs with full options table, constraints, NFRs, revisit conditions |
| Quality requirements | arc42 §10 | NFRs as measurable quality scenarios (referenced from ADRs) |
| Risks | arc42 §11 | Known problems and their priority |
| Glossary | arc42 §12 | Domain term definitions |

**For this developer toolkit**, sections 2, 7, 10, 11, 12 are optional / lightweight. The core is: §1 (why), §3 (context), §4 (strategy), §5 (building blocks = construct registry), §8 (crosscutting = patterns.md), §9 (decisions = ADRs).

### arc42 §5 Building Block View = The Construct Registry Hierarchy

arc42's building block view uses a **black box / white box** model across levels:

- **Black box**: shows a construct only by its responsibility and interfaces — internals hidden. This is what the L0 index shows.
- **White box**: opens up a black box to show its internal composition. This is what a construct file shows.

The levels:

```
Level 0 (black box)  — docs/registry/index.md
                        The "Does" column. One line per construct.
                        What it does. Not how.

Level 1 (white box)  — docs/registry/constructs/<Name>.md
                        Full interface, dependencies, FR list, proof.
                        How it works externally — not internal implementation.

Level 2 (source)     — the actual source file
                        Read only when you need to understand or modify internals.
                        Not documentation — this is the code itself.
```

**arc42's Level 1 sufficiency principle**: "The Level 1 building block view is often sufficient for most stakeholders." This is the designed sufficiency gate — most questions are answered at Level 0 or Level 1 without ever touching the source.

### HTML as First-Class Output

Markdown is the **source of truth** — git-diffable, agent-readable, version-controlled. HTML is the **rendered view** — interactive, visual, navigable by humans. They are the same content in two formats.

doc-maintainer generates and regenerates `docs/index.html` alongside every markdown update. The HTML is committed to the repo. Developers open `docs/index.html` in a browser — they never need to read raw markdown tables.

The HTML renders:
- arc42 sections as navigable chapters
- C4 diagrams as interactive SVGs (not static images)
- The construct registry as a searchable, filterable table
- The feature cross-reference as a clickable graph
- ADRs with the options table rendered visually
- The 3 worked examples below, interactive (click a persona, see the reading path highlighted)

## Sufficiency Gates — Explicit per Reader Persona

The sufficiency gate is the decision point: "do I have enough context to proceed, or do I need to go deeper?" arc42 leaves this to the author. We make it explicit and operational.

| Reader / Task | Start | Gate condition | If gate passes | If gate fails — go to |
|---|---|---|---|---|
| "Does X exist?" | L0 "Does" column search | Found a match | Use existing construct | L0 Feature Cross-Ref, then construct file |
| "What touches auth?" | L0 Feature Cross-Ref row | Got construct list | Done — have the full picture | Construct files for each listed construct |
| "How does X work?" | L0 construct row | Got one-liner | Done for quick understanding | Construct file (Level 1 white box) |
| "Why was X built this way?" | decisions/index.md | Found relevant ADR title | Read that ADR | Construct file's Key Decisions section |
| "I'm modifying X — what breaks?" | Construct file "Called by" | Got caller list | Done — know blast radius | Arc42 §6 runtime scenario for X |
| "New team member onboarding" | arc42 §1 → §3 → §4 | Have mental model of system purpose | Read L0 construct table | arc42 §5 Level 1 for specific areas |
| "New agent session — where am I?" | CLAUDE.md → L0 | Have domain map + known gaps | Proceed with task | Construct file for relevant constructs |
| "Debug — why is X failing?" | arc42 §6 runtime scenario | Have the call sequence | Trace through it | Construct files for suspects |

### Example 1: Agent — "Add a refund flow to orders"

**Context**: task-executor is starting a new task. It has never seen this codebase.

**Step 1** — reads `docs/registry/index.md` (L0, always, 80 lines max)

The agent scans the "Does" column for anything related to refunds, payments, orders:

OrderService      Manages order lifecycle and state transitions         verified

```

Feature Cross-Reference:
```

```

**Sufficiency gate check**: Does the agent have enough to proceed?
- It knows what exists in the orders domain ✓
- It sees "charges only" on PaymentAdapter — signals refund may not be there ✓
- But it doesn't know whether there's *any* refund logic anywhere else ✗

**Gate fails — go deeper.**

**Step 2** — reads `docs/registry/constructs/PaymentAdapter.md`

Finds in the "Does" section: *"Handles Stripe charges via the charge API. Does NOT handle refunds — Stripe refund endpoint not yet wired."* FR list confirms: refund is listed as a planned FR with `status: planned`, no proof yet.

**Sufficiency gate check**:
- Confirmed: no refund logic exists anywhere ✓
- Knows the boundary (PaymentAdapter owns payment, refund endpoint not wired) ✓
- Knows this is genuinely new work, not a duplicate ✓

**Gate passes. Stops here. Does not read source code.**

**Total reads: 2. Source code reads: 0. Duplicate check: passed.**

## Design Principles (Non-Negotiable)

**1. Construct-centric, not feature-centric or file-centric.**
Features come and go as a way of organising work. File locations are framework conventions (React uses `src/pages/`, `src/services/`; backend uses `src/controllers/`, `src/repositories/`). Neither is stable enough to be the indexing unit. The construct — the class, service, component, model, resource — is what persists.

**2. Capability search, not path search.**
"Does something that handles JWT validation already exist?" must be answerable without reading source code. The registry is indexed by what constructs do, not where they live.

**3. Cross-layer feature view.**
"Show me everything about auth" must traverse all layers: which pages, which API endpoints, which services, which models, which infra resources. Features are cross-cutting concerns that span the entire stack. The registry must support this traversal.

**4. Construct lifecycle with proof.**
Every construct has a state: `planned → built → verified → diverged`. The transition from `built` to `verified` requires proof against Functional Requirements. The transition to `diverged` requires an ADR capturing why reality forced a pivot.

**5. FR per construct. NFR + patterns per ADR.**
Functional Requirements belong on constructs — they are specific and provable. Non-Functional Requirements (performance, security, reliability) are cross-cutting system-level decisions and belong in ADRs with full context and revisit conditions.

**6. Every skill reads before it acts, writes after it acts.**
The registry is not maintained by doc-maintainer alone. init, plan, explore, task-executor, and the new /adr skill all read from and write to it. doc-maintainer is the consistency guardian, not the sole writer.

**7. Progressive disclosure — reads scale with task scope, not codebase size.**
A duplicate check costs 2 reads at 5 features and 2 reads at 200 features. Source code is only read when the registry has a gap.

**8. Bidirectional traceability, agent-maintained.**
Every spec links forward to its constructs. Every construct links back to the spec that planned it and the proof that verified it. This is impossible for a human maintainer to keep in sync at scale. An agent running daily can enforce it mechanically.

## The Construct Lifecycle

```
PLANNED    Spec approved, construct described but not yet built.
           Written by: plan (after spec approval)
           Contains: planned FR, planned interface, planned dependencies

BUILT      task-executor has implemented it and committed.
           Written by: task-executor (post-task)
           Contains: real file location, real interface, real dependencies
           Missing: proof against FR

VERIFIED   Post-hook validator confirmed it meets all FRs.
           Written by: post-hook validator
           Contains: proof method, checklist result, test file (future)

DIVERGED   Implementation diverged from spec. ADR written explaining why.
           Written by: /adr (triggered by validator or developer)
           Contains: link to ADR, what changed, what the new contract is
           Note: DIVERGED is not failure. It is an honest record of reality.
```

The transition `BUILT → VERIFIED` requires a human to walk a checklist derived from the FRs.
The transition `BUILT → DIVERGED` requires an ADR before the next task can run.
Future: `VERIFIED` via automated test or unit test replaces human checklist.

## Registry Structure

```
docs/registry/
├── index.md                          # L0 — global construct index (hard limit: 80 lines)
│                                     #   capability search surface
│                                     #   cross-layer feature view entry point
│                                     #   known gaps list
│
├── constructs/
│   ├── <ConstructName>.md            # one file per construct (no size limit)
│   └── ...
│
├── patterns.md                       # cross-cutting conventions
│                                     #   written by /adr when a decision establishes a pattern
│                                     #   each pattern links to its ADR and implementing constructs
│
└── decisions/
    ├── index.md                      # ADR index (id | date | status | decision | affects)
    └── <NNN>-<title>.md             # one ADR per significant decision (MADR format)
```

### Why not subdirectories per domain or per layer?

Because the codebase isn't organised by domain — it's organised by layer and framework convention (`src/services/`, `src/pages/`, `src/utils/`). Imposing a domain structure on the registry that doesn't match the source tree creates a permanent translation problem.

And because "auth" is a cross-cutting concern that spans frontend, backend, database, and infra. It is not a folder. It is a capability. The registry reflects capabilities, not folders.

## Construct File — `docs/registry/constructs/<ConstructName>.md`

One file per construct. No size limit — detail lives here.

```markdown
---
name: UserAuthService
type: Service
layer: Backend
file: src/services/auth.ts
status: verified        # planned | built | verified | diverged
planned_in: specs/auth/overview.md
last_verified: YYYY-MM-DD
---

## Does

Validates JWT tokens and manages user sessions. Does NOT handle OAuth flows
(see OAuthService) or password hashing (see UserRepository).

## Functional Requirements

- [ x ] User can authenticate with valid email + password → returns session token
- [ x ] Invalid credentials return 401, never 500
- [ x ] Expired tokens are rejected and session is cleaned up
- [ x ] Max 5 concurrent sessions per user enforced

## Proof

- method: human
- verified_by: daniel.k 2026-04-15
- checklist_result: all 4 FRs passed
- test_file: null  ← future: src/services/__tests__/auth.test.ts

## Interface

```typescript
class UserAuthService {
  validateToken(token: string): Promise<UserContext | null>
  createSession(userId: string, deviceInfo: DeviceInfo): Promise<Session>
  revokeSession(sessionId: string): Promise<void>
  revokeAllSessions(userId: string): Promise<void>
}
```

## Dependencies

- Calls: SessionRepository, bcrypt (external)
- Called by: AuthMiddleware, LoginController
- Reads: sessions (model), users (model)
- Writes: sessions (model)

## Patterns Applied

- [JWT over session cookies](decisions/003-jwt-vs-session-cookies.md)
- [Soft-delete: NOT applied](patterns.md#soft-delete) — sessions are hard-deleted on expiry (see ADR-005)

## Key Decisions

- [ADR-003](decisions/003-jwt-vs-session-cookies.md) — Stateless JWT chosen over server-side sessions
- [ADR-005](decisions/005-session-expiry.md) — Sessions hard-deleted, not soft-deleted
```

## ADR File — `docs/registry/decisions/<NNN>-<title>.md`

MADR format. Written at decision time by the `/adr` skill. NFRs live here.

```markdown
---
id: "003"
date: YYYY-MM-DD
status: Accepted
deciders: [daniel.k, lead-engineer]
affects: [UserAuthService, AuthMiddleware, sessions]
---

## Context

We need to handle user authentication across a stateless API. Team size: 2 engineers.
No compliance requirement for server-side session storage. Expected scale: < 10k users
at launch. Timeline: 3 weeks to MVP.

## Decision

We will use stateless JWT tokens for authentication, not server-side sessions.

## Options Considered

| Option | Pros | Cons | Why rejected |
|--------|------|------|--------------|
| **JWT (chosen)** | Stateless, no DB lookup per request, scales horizontally | Token revocation is complex, larger payload | — chosen |
| Server-side sessions | Easy revocation, smaller token | DB lookup every request, horizontal scaling needs sticky sessions or Redis | Over-engineered for current scale; adds Redis dependency |
| OAuth only | Industry standard, delegates auth | Too complex for MVP, requires external provider setup | Out of scope for 3-week timeline |

## NFR Captured

- Auth response time < 100ms p95 (JWT eliminates DB lookup on validation)
- No plaintext credentials stored at any point (bcrypt min rounds: 12)

## Consequences

**Now easier**: Horizontal scaling, no session store dependency.
**Now harder**: Token revocation requires blacklist (implemented in SessionRepository).
**New constraints**: Refresh token rotation must be implemented before launch.

## Revisit Conditions

If we need real-time session revocation (e.g. compliance requirement),
or if team grows past 5 engineers and session management becomes complex.
```

## patterns.md — `docs/registry/patterns.md`

Written by `/adr` when a decision establishes a cross-cutting convention.

```markdown
# Established Patterns

> These are non-negotiable conventions. Before implementing anything,
> check if a pattern applies. If you need to deviate, write an ADR.

## Soft Delete

All entities use soft-delete (`deletedAt DateTime?`). Hard deletes are never used
except for session tokens (see ADR-005).
- Implements: User, Order, Product, Notification
- ADR: [ADR-002](decisions/002-soft-delete-strategy.md)

## Auth Pattern

All authentication is JWT-based. No server-side session storage.
- Implements: UserAuthService, AuthMiddleware
- ADR: [ADR-003](decisions/003-jwt-vs-session-cookies.md)

## API Response Envelope

All API responses follow: `{ data, error, meta }`.
Never return naked arrays or raw model objects.
- ADR: [ADR-004](decisions/004-api-response-shape.md)

## Anti-Patterns

- ❌ Do not store auth state in React component state — use the auth context
- ❌ Do not call the database directly from controllers — always go through a repository
- ❌ Do not use `any` type in TypeScript — use unknown + type guards
```

## Skill Integration

### `init` skill

**Greenfield:**
- Creates `docs/registry/index.md` shell (empty constructs table, empty feature cross-reference)
- Creates `docs/registry/decisions/index.md` shell
- Creates `docs/registry/patterns.md` shell
- Writes ADR-001: stack rationale (framework, cloud, ORM, auth approach chosen during init)
- Injects agent navigation protocol into project `CLAUDE.md`

**Brownfield (new `brownfield-migrate` mode):**
- Reads all existing `specs/*/overview.md` → extracts constructs from Implementation Order sections → creates construct files with `status: planned` (were they actually built? unknown)
- Reads `src/` directory listing → finds files → matches against spec constructs → promotes matches to `status: built` (unverified)
- Reads schema file once → registers all data models
- Greps IaC files → registers all infrastructure resources
- Runs `git log --name-only -20` → highest-churn files get priority stub entries
- Generates migration report: N planned, N built (unverified), N unknown, N known gaps
- Hard limit: 5 source file reads during seeding pass

**Result:** A partially-populated registry that is honest about what it doesn't know. More useful than nothing. doc-maintainer fills gaps from there.

### `plan` skill

**Before designing (Phase 2):**
1. Read `docs/registry/index.md` (L0)
2. Search "Does" column for concepts similar to what the user wants to build
3. Check Feature Cross-Reference for related features
4. Present findings: "These constructs already exist and may be relevant: ..."
5. Invoke `explore` **only** if L0 has Known Gaps in the relevant area

**After spec approval (Phase 5):**
- For each planned construct: create `docs/registry/constructs/<Name>.md` with `status: planned`
- Populate FR section from spec requirements
- Populate planned interface from spec design
- Append row to L0 index (Name | Type | Does | Layer | File=TBD | Status=planned)
- Append to Feature Cross-Reference table

**What this prevents:**
- Duplicate prevention: L0 "Does" column search catches semantic duplicates before design begins
- Re-scan prevention: 1 file read (L0) replaces full explore traversal for known areas

### `explore` skill

**New Tier 1:**
1. Read `docs/registry/index.md` (L0)
2. If registry covers the focus area and has no Known Gaps → **sufficiency gate passes. Return registry content. Do not read source code.**
3. If Known Gaps exist for focus area → scope source read to those specific areas only

**After investigation:**
- New constructs found: create construct files with `status: built` (unverified)
- Append to L0 index
- Remove filled Known Gaps from L0
- Add new Known Gaps discovered

### `task-executor` skill

**Before each task (mandatory):**
1. Read `docs/registry/index.md` (L0)
2. Search for constructs the task will create or modify
3. If `status: planned` → read construct file for planned interface. Implement to match.
4. If `status: active/verified` → do not recreate. Extend or call it.
5. If not in registry → confirm genuinely new. Proceed.

**After each task:**
- New construct: create construct file with `status: built`, real file location, real interface, real dependencies
- Stub promoted: update existing construct file from `planned` to `built`
- Modified construct: update interface section, reset status to `built` (needs re-verification)
- Update L0 index row
- Write forward dependency links in own construct file
- Note cross-domain dependencies (doc-maintainer will write back-links on next cron run)

**Post-task: trigger post-hook validator**

### Post-Hook Validator (new — Phase 3)

Runs automatically after every task-executor commit.

For each construct touched in the commit:
1. Read its construct file
2. Check `status` — if `planned` or `built`, run FR verification
3. Generate human checklist from FR list
4. Present to developer: "Task complete. Please verify these FRs before the next task runs:"
   ```
   UserAuthService — 4 FRs to verify:
   [ ] User can authenticate with valid email + password → returns session token
   [ ] Invalid credentials return 401, never 500
   [ ] Expired tokens are rejected
   [ ] Max 5 concurrent sessions enforced
   ```
5. Developer marks each FR pass/fail
6. All pass → update construct file to `status: verified`, write proof block
7. Any fail → construct stays `built`, flag as incomplete (not DIVERGED — just unfinished)
8. If developer indicates implementation diverged from spec → trigger `/adr` before next task runs. Next task is blocked until ADR is written.

**Future:** Steps 4-6 replaced by automated test run against FR list.

---

### `/adr` skill (new)

Two triggers:
1. Developer explicitly runs `/adr` at a decision point
2. Post-hook validator detects a divergence and triggers it automatically

**Phases:**
1. "What did you decide?" (one sentence)
2. "What alternatives did you consider?" (list)
3. "What constraints were active?" (team size, cost, timeline, compliance, scale)
4. "Does this establish a cross-cutting pattern?" → if yes, also write to `patterns.md`
5. "What NFRs does this decision enforce?" (performance, security, reliability targets)
6. "What should trigger a revisit?"
7. "Which constructs does this affect?" (links back to construct files)
8. Generate options table, show for confirmation
9. Write `docs/registry/decisions/<NNN>-<title>.md`
10. Append row to `decisions/index.md`
11. For each affected construct: add `Key Decisions` link to construct file
12. If pattern established: append to `patterns.md` with ADR link

---

### `doc-maintainer` skill

**Role:** Consistency guardian and gap filler. Not the primary writer.

**Per cron run, in priority order:**

1. **Bidirectional link check**: every spec has forward links to constructs; every construct has back link to spec. Broken links → flag in Known Gaps.
2. **Back-link reconciliation**: read construct files for cross-domain `Calls` entries. Write corresponding `Called by` entries in the called construct's file.
3. **Stub verification** (3 per run, oldest first): find `status: planned` construct files. Check if file exists at planned path. If yes → promote to `built`. If no → keep as `planned`, note in Known Gaps.
4. **Staleness check** (`last_verified` > 60 days): read source file, check interface still matches. Update or flag `stale`.
5. **Known Gaps reduction** (1 gap per run): pick oldest gap. Read that source directory. Create stub entries for found constructs.
6. **L0 size guard**: if L0 exceeds 80 lines → flag to user. Suggest splitting Feature Cross-Reference into a separate file.
7. **Existing C4 doc passes** (unchanged).

**Hard limits per run:** max 8 source file reads, max 3 construct files created or updated, max 1 ADR written.

## Phased Implementation

### Phase 1 — Foundation (delivers value immediately)
- Registry structure + L0 index format
- `docs/registry/constructs/` file format + templates
- `docs/registry/patterns.md` format
- `/adr` skill (new)
- `doc-maintainer` consistency pass + bidirectional link enforcement
- `init` greenfield registry bootstrap + ADR-001 auto-population
- `brownfield-migrate` mode on `init`

**Value:** Decisions get captured. Patterns are explicit. Bidirectional links enforced automatically. Any repo can adopt immediately.

### Phase 2 — Planning integration
- `plan` reads L0 before designing (capability search)
- `plan` writes construct stubs + L0 rows after approval
- `explore` uses registry as Tier 1, writes gaps after investigation
- Feature Cross-Reference table maintained by plan

**Value:** Duplicate prevention during planning. explore invoked only for Known Gaps.

### Phase 3 — Execution integration
- `task-executor` mandatory pre-task L0 read
- `task-executor` post-task construct file write
- Post-hook validator (FR checklist, verified/diverged flow)
- `/adr` triggered automatically on divergence detection

**Value:** Full lifecycle loop. Every construct tracked from planned → verified or diverged. Decisions captured at the moment of pivot.

### Phase 4 — Automated proof (future scope)
- Unit test generator from FR list
- Automated test runner against construct FRs
- `status: verified` set by test runner, not human checklist

**Value:** Human checklist becomes optional. Verification is continuous, not manual.

### Phase 5 — Bug remediation skill (future scope)

A bug fix is a state transition in the construct registry, not just a code change. When a fix changes behaviour that was previously verified, the registry must reflect that — otherwise it lies.

**`/bug` skill flow:**
1. Read L0 — locate the affected construct
2. Read construct file — understand the documented FRs and what the bug violates
3. Check "Called by" — establish blast radius before touching anything
4. Fix implemented and committed
5. Post-hook validator re-runs — all FRs must re-pass, not just the broken one. Status resets to `built` until re-verified.
6. Two outcomes:
   - **Fix restores original behaviour** → re-verify → back to `verified`
   - **Fix changes the contract** (e.g. error response shape changes) → `/adr` triggered → `diverged` → new contract documented

**Key principle:** The bug skill is anchored in what's already implemented — it reads the registry, understands the contract, fixes the violation, and updates the proof. It never re-derives the system from source code.

**Dependency on Phase 4:** The `/bug` skill is most powerful once automated tests exist — a failing test identifies the violated FR precisely, and the test suite confirms restoration after the fix.

## Brownfield Migration Path (Existing Kit Users)

For repos that have already used the kit — existing specs, C4 docs, code — migration is non-destructive.

```
init brownfield-migrate:
  1. Read all existing specs/*/overview.md
  2. Extract constructs from Implementation Order sections
  3. Create construct files with status: planned
     (were they actually built? unknown until verification)
  4. Walk src/ — match files against planned construct locations
  5. Matches → promote to status: built (unverified)
  6. No match → keep as planned (never built, or path changed)
  7. Read schema file → register all data models as built (unverified)
  8. Grep IaC files → register all infra resources as built (unverified)
  9. Generate migration report:
       N constructs registered from specs
       N promoted to built (found in src/)
       N still planned (not found — investigate)
       N data models registered
       N infra resources registered
       N known gaps (src/ areas with no spec coverage)
  10. doc-maintainer takes over from here on next cron run
```

No existing files are touched. No specs are modified. The registry starts populated from what you already have. The transition is invisible to ongoing work.

## Open Questions (Implementation-Level, Not Design-Level)

1. **ORM detection breadth**: Data model seeding is straightforward for Prisma. Should v1 also handle TypeORM, SQLAlchemy, Django models, or raw SQL migrations — or mark them as Known Gaps with a note?

2. **Parallel session safety**: If plan and task-executor both append to L0 in the same session (planning one feature while executing another), is file-level append safe? Or do we need a simple lock file convention?

3. **FR extraction from existing specs**: Existing spec files use "Implementation Order" sections, not explicit FR lists. The brownfield migration needs a heuristic to extract FRs. Should it prompt the user to confirm extracted FRs, or generate a best-effort list and flag for review?
