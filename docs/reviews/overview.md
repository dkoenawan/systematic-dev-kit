# Reviews

## What Is Reviews?

Reviews is a skill test-run record and failure-pattern library for improving skill definitions. The primary object it owns is a **SkillReview** — a structured markdown document that records a single test run of a skill, capturing what the user asked, which phases executed, where the skill deviated from its intended workflow, why it failed, and what specific change to `SKILL.md` would fix it. Over time, the reviews directory becomes a searchable diagnostic library that accelerates skill debugging by encoding known failure modes.

## How It Works

A SkillReview is created after a developer observes a skill behaving incorrectly during a manual test run. The developer copies `TEMPLATE.md` into `reviews/<skill-name>/YYYYMMDD_<short-description>.md` and fills in five sections: Invocation (exact input used), What Happened (observed vs. expected behaviour), Root Cause Analysis (which failure pattern applies and why), Recommended Fix (the exact `SKILL.md` wording change — current → proposed), and a Follow-up Checklist.

The developer maps the failure to one of three canonical failure patterns documented in `README.md`: Natural Stopping Points (a sub-skill return creates a "beat" the model misreads as completion), Declarative vs. Evaluative Instructions (descriptive language is treated as documentation rather than a requirement), or Weak Transition Language (soft directives are treated as suggestions). If the failure is novel, it is documented as a new pattern. The recommended fix is applied to the relevant `SKILL.md`, the test is re-run, and the Follow-up Checklist is updated.

## Core Objects / Entities

| Object | Description |
| ------ | ----------- |
| `SkillReview` | A dated markdown record of one skill test run: invocation, observed behaviour, root cause, recommended fix, and verification status. |
| `FailurePattern` | A named category of skill definition failure with a diagnostic signature and a standard fix template. Three canonical patterns are currently documented. |
| `RecommendedFix` | A concrete before/after diff of the relevant `SKILL.md` section, ready to apply. |

## Code Map — Which Code Touches This

- **Models / Schema**: `reviews/TEMPLATE.md` — canonical structure for all SkillReview documents (sections: Invocation, What Happened, Root Cause Analysis, Recommended Fix, Follow-up Checklist).
- **Business Logic / Services**: `reviews/README.md` — defines the review system, file naming convention (`YYYYMMDD_<short-description>.md`), three canonical failure patterns, and the debugging workflow.
- **API / Interface**: No programmatic interface — reviews are created and read manually by developers.
- **Persistence**: `reviews/<skill-name>/` subdirectories contain dated review files; e.g., `reviews/plan/20260309_weekly-assessment.md`.
- **External callers**: `skills/*/SKILL.md` files are the subjects of recommended fixes documented in reviews; the reviews reference specific line numbers and excerpts from those files.

## Internal Architecture

**Review-Driven Improvement Loop**: Reviews are not standalone bug reports — they are a feedback mechanism for hardening skill definitions against LLM interpretation failures. Each review proposes a specific diff to `SKILL.md`, making the fix directly actionable. The three canonical patterns encode reusable solutions: replace soft transitions with **MANDATORY CONTINUATION POINT** labels; replace descriptive requirements with **SKILL COMPLETION GATE** binary checklists; replace directional cues with imperative scope language ("in this same response").

## Dependencies

- **Internal**: All skills in `skills/*/` are potential subjects of reviews; `reviews/plan/` contains the first concrete example.
- **External**: None — reviews are pure markdown documentation.

## Gotchas

- Reviews document manual test observations, not automated regression tests. The same failure can reoccur months later if the recommended fix was not applied or was later reverted; the review history must be searched proactively when debugging recurring issues.
- The Follow-up Checklist's "Fix applied" checkbox relies on developer discipline — a review can be filed but its fix left unapplied indefinitely.
- Sub-skill return transitions are documented as the highest-risk failure class (the `plan/20260309` review demonstrates the pattern). Any skill that chains sub-skills should be treated as likely to need defensive continuation wording.
- None identified at time of writing regarding the review system's own file naming or search conventions.
