The System Model
— finalised design

Every design question from v1 is resolved. This document is the agreed architecture before spec finalisation and implementation planning.

01 The real problem (precisely stated)

Feature specs work. The failure mode is specific and concrete:

Root cause
A construct gets built as part of a feature — a utility class, a service, a helper — and six months later nobody remembers it exists. The next agent or developer building a new feature creates a duplicate because they had no way to know it was there. The spec that captured it is a feature-level snapshot. There is no system-level index of what exists and what it does.

The solution is not more feature-level documentation. It is a construct registry — a living index of every significant construct in the system, indexed by what it does, maintained by every skill, and queryable before any new construct is created.

And alongside that: a decision record layer that captures why things were built the way they were — at the moment the decision was made, with the full options table and the active constraints — so that six months later a developer doesn't re-derive a decision and come to a different conclusion.

02 Design principles

Construct-centric, not feature-centric or file-centric

Features are a way of organising work — they come and go. File locations are framework conventions (src/pages/, src/services/, src/utils/) — they reflect layer, not capability. The construct is what persists. It is the right indexing unit.

Capability search, not path search

"Does something that handles JWT validation already exist?" must be answerable without reading source code. The registry is indexed by what constructs do, in a "Does" column that is searched before any new construct is proposed.

Cross-layer feature view

"Show me everything about auth" must traverse all layers: which pages, which API endpoints, which services, which models, which infra resources. A Feature Cross-Reference table in the L0 index provides this in one read.

FR per construct. NFR + patterns per ADR.

Functional Requirements are specific, per-construct, and provable. They live on the construct file. Non-Functional Requirements (performance, security, reliability) are cross-cutting system-level decisions. They live in ADRs with full context, constraints, and revisit conditions.

Every skill reads before it acts, writes after it acts

The registry is not maintained by doc-maintainer alone. init, plan, explore, task-executor, and /adr all read and write it. doc-maintainer is the consistency guardian — not the sole writer.

Progressive disclosure

A duplicate check costs 2 reads at 5 features and 2 reads at 200 features. Source code is only read when the registry has a Known Gap. The read cost scales with task scope, not codebase size.

Bidirectional traceability, agent-maintained

Impossible for a human to keep in sync at scale. Mechanical for an agent running daily. doc-maintainer owns link reconciliation.

03 Construct lifecycle

Every construct in the registry has a state. The state tracks the gap between what was planned and what was actually built and verified.

Planned
Written by: plan
Spec approved. Construct described but not yet built. FR list established. Planned interface documented.
Built
Written by: task-executor
Implemented and committed. Real file location, real interface, real dependencies. FRs not yet verified.
Verified
Written by: post-hook validator
All FRs passed. Human checklist completed. Future: automated test confirms it. Proof block written.
Diverged
Written by: /adr
Implementation diverged from spec. ADR written capturing why. New contract documented. Not failure — honest record of reality.
planned → built → verified (or diverged)
The critical transition: built → verified requires proof against FRs. built → diverged requires an ADR before the next task-executor task can run. This is the moment decisions get captured — not reconstructed six months later.

Proof methods (in order of maturity)

Right now: human verifiable — a checklist derived from the FR list that a developer can walk through in under 5 minutes. Future: automated test pointing to a test file. Further future: unit test generated from the FR list automatically. All three slot into the same proof block on the construct file.

NFRs are ADR-only

Performance targets, security requirements, reliability SLAs — these are cross-cutting decisions with context and history. They belong in ADRs, not on individual construct files. An ADR captures the NFR, the constraint that drove it, and the condition under which it should be revisited.

04 Registry structure

docs/registry/
│
├── index.md                     # L0 — the capability search surface (hard limit: 80 lines)
│                                #   "Does" column — search this before creating anything
│                                #   Feature cross-reference — auth touches these 4 constructs
│                                #   Known gaps — areas not yet registered
│
├── constructs/
│   ├── UserAuthService.md          # one file per construct, no size limit
│   ├── LoginPage.md                #   status: planned | built | verified | diverged
│   ├── SessionRepository.md        #   FR list + proof block
│   ├── formatCurrency.md           #   interface, dependencies, decisions, patterns applied
│   └── ...                         #   back-link to spec that planned it
│
├── patterns.md                      # cross-cutting conventions
│                                #   written by /adr when a decision establishes a pattern
│                                #   soft-delete, auth approach, API envelope, anti-patterns
│                                #   each entry links to its ADR and implementing constructs
│
└── decisions/
    ├── index.md                    # id | date | status | decision | affects
    ├── 001-stack-rationale.md      # ADR-001: always written by init
    ├── 003-jwt-vs-sessions.md      # MADR format: context, options table, NFRs,
    └── 007-functions-vs-servicebus.md #   consequences, revisit conditions

Why not domain directories or layer directories?

The codebase is organised by framework convention — src/services/, src/pages/, src/utils/ — not by domain. And "auth" as a concept spans all layers. Imposing a domain structure on the registry that doesn't match the source tree creates a permanent translation problem. The flat constructs/ directory plus the L0 Feature Cross-Reference table gives you both capability search and cross-layer feature view without requiring the source to be domain-organised.

L0 index — the only file always read

Hard limit: 80 lines. Contains the construct table with a "Does" column — a one-line capability description written to be searched, not just read. Before any skill proposes a new construct, it searches this column. "Formats numbers" → finds formatCurrency. Duplicate prevented.

The 80-line L0 limit is what makes this work. If L0 grows past 80 lines, doc-maintainer flags it. The Feature Cross-Reference section moves to a separate file. The construct table remains. The read cost never grows.

07 Post-hook validator flow

Runs automatically after every task-executor commit. This is the mechanism that moves constructs from built to verified or diverged.

1
Read construct files for all constructs touched in the commit.
2
For each construct: does the file exist at the documented path?
Yes — continue No — flag as incomplete, keep status: built
3
Generate human FR checklist from the construct's FR list. Present to developer:

UserAuthService — 4 FRs to verify:
[ ] User authenticates with valid email + password → session token returned
[ ] Invalid credentials → 401, never 500
[ ] Expired tokens rejected, session cleaned up
[ ] Max 5 concurrent sessions per user enforced
4
Developer marks each FR.
All pass → status: verified, proof block written Any fail → keep status: built, flag FR as failing
5
Developer signals divergence (implementation changed from plan).
Diverged → /adr triggered. Next task blocked until ADR is written and status: diverged is set.
Why block the next task on divergence? Because the decision — "we changed the approach because of X" — must be captured at the moment it's made. If the next task runs first, the context is lost. The developer is still in the problem space. The ADR takes 5 minutes. Six months from now it saves hours.

08 /adr skill

The /adr skill captures decisions at the moment they are made — not reconstructed later. It has two triggers: explicit invocation by the developer, and automatic triggering by the post-hook validator on divergence detection.

It asks 6 questions in sequence, then generates the MADR file:

1
"What did you decide?" — one sentence.
2
"What alternatives did you consider?" — builds the options table.
3
"What constraints were active?" — team size, cost, timeline, compliance, scale expectations. These explain the choice to future readers.
4
"Does this establish a cross-cutting pattern?" — if yes, also writes to patterns.md with ADR link.
5
"What NFRs does this decision enforce?" — performance targets, security requirements, reliability SLAs. These live here, not on constructs.
6
"What should trigger a revisit?" — specific conditions, not vague. "If order volume exceeds 5,000/day" not "if we need to scale".

After confirmation: writes decisions/NNN-title.md, appends to decisions/index.md, adds Key Decisions links to affected construct files, and (if pattern) appends to patterns.md.

09 All 6 decisions resolved

Q1 Domain boundaries on brownfield — how should init classify the existing codebase?
Domain classification is the wrong model entirely. Most codebases are organised by framework layer (src/services/, src/pages/, src/utils/) not by domain — and that's correct per framework conventions. The registry doesn't impose a domain structure that doesn't exist. Instead: a flat constructs/ directory, indexed by capability. The L0 "Does" column is the search surface. The Feature Cross-Reference table gives the cross-layer view. No domain boundaries required.
Q2 Stubs — should plan write speculative entries before code exists?
Yes, but the validator is the enforcement mechanism. Plan writes construct files with status: planned and an FR list. The post-hook validator is what catches divergence — not careful stub design. This means a parallel feature planning the same construct will see it in L0 before either is built. Duplicate prevention works even during the planning phase, before a single line of code is written.
Q3 Cross-domain back-links — who writes "Called by" entries?
Hybrid — task-executor writes forward links, doc-maintainer reconciles back-links. task-executor writes Calls: UserAuthService in the orders construct file. doc-maintainer reads that on its next cron run and writes Called by: OrderService in the auth construct file. Clean separation: task-executor stays focused on its domain, doc-maintainer handles cross-domain consistency.
Q4 patterns.md ownership — who writes it and when?
/adr writes it when a decision establishes a cross-cutting pattern. Not doc-maintainer inferring from code. Not a manually-maintained file. When a developer captures a decision with /adr and marks it as pattern-establishing, /adr writes the pattern entry with a link back to the ADR. Patterns are documented at decision time, with full context, not reverse-engineered later.
Q5 Bidirectional traceability — spec ↔ registry — is it maintainable?
Yes, because agents maintain it, not humans. Every spec links forward to its construct files. Every construct file links back to the spec that planned it. doc-maintainer's daily cron run checks and repairs these links mechanically. Broken links surface in Known Gaps. A human maintainer keeping these in sync at scale is impossible. An agent doing it daily is trivial.
Q6 Phased vs. all-at-once implementation?
Phased. All-at-once means nothing works until everything works. Each phase delivers independent value. Phase 1 (foundation + /adr + doc-maintainer + init) can be used immediately on any repo. Phase 2 adds planning integration. Phase 3 adds the full verified/diverged loop. Phase 4 replaces human checklists with automated tests.

11 Brownfield migration path

For repos that have already used the kit — existing specs, C4 docs, running code. Migration is non-destructive. No existing files are touched until the agent has verified what's there.

  • Read all existing specs/*/overview.md — extract constructs from Implementation Order sections. Create construct files with status: planned.
  • Walk src/ — match files against planned construct locations. Matches → promote to status: built (unverified). No match → keep as planned (never built, or path changed).
  • Read schema file once → register all data models as built (unverified).
  • Grep IaC files → register all infra resources as built (unverified).
  • Run git log --name-only -20 → highest-churn files get priority stub entries in Known Gaps.
  • Generate migration report: N planned, N built (unverified), N still planned (not found), N data models, N infra resources, N known gaps.
  • doc-maintainer takes over. Each cron run fills 1 Known Gap, verifies 3 stubs. Registry becomes complete over time without a big-bang migration event.
Hard limit during seeding: 5 source file reads total. The migration report is generated from structure analysis, not deep code reading. Completeness comes from doc-maintainer's incremental runs, not from the init pass trying to do everything at once.

12 Remaining implementation questions

Design is resolved. These are implementation-level questions for the task-executor planning phase:

I1 ORM detection breadth for brownfield migration
Data model seeding is straightforward for Prisma (single schema file). Should v1 also detect TypeORM (src/entities/*.ts), SQLAlchemy, Django models — or mark non-Prisma repos as a Known Gap?
I2 Parallel session safety on L0 append
If plan and task-executor both append to L0 in the same session (planning one feature while executing another), is file-level append safe? Or do we need a simple lock file convention?
I3 FR extraction from existing specs
Existing spec files use Implementation Order sections, not explicit FR lists. The brownfield migration needs a heuristic to extract FRs, or it prompts the developer to confirm. Which is better for v1?
