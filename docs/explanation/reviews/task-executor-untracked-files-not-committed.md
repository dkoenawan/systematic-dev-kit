# RCA: task-executor Left Frontend Pages and Spec Docs Untracked

## Metadata
- **GitHub Issue**: [#79](https://github.com/dkoenawan/MithrilLedger/issues/79)
- **Date**: 2026-06-27
- **Branch**: `feat/category-management`
- **PR**: [#80](https://github.com/dkoenawan/MithrilLedger/pull/80)
- **Status**: Resolved
- **Severity**: Medium (feature code shipped without being in the PR; discovered during manual review)

## Summary

The `compass-labs:task-executor` skill completed all 9 tasks for issue #79 and marked the plan as done, but left 17 files untracked in the working tree. These included the entire `frontend/src/pages/categories/` and `frontend/src/pages/transactions/` directories (15 files, 1,349 lines of React code) and two spec docs (`specs/category-management/overview.md`, `specs/category-management/erd.html`). The PR was opened and mergeable, but did not include this code.

## What Was Missing

| Path | Files | Status |
|---|---|---|
| `frontend/src/pages/categories/` | 9 | Untracked — never committed |
| `frontend/src/pages/transactions/` | 6 | Untracked — never committed |
| `specs/category-management/overview.md` | 1 | Untracked — never committed |
| `specs/category-management/erd.html` | 1 | Untracked — never committed |

`specs/category-management/tasks.md` was already tracked (committed by the task-executor initialisation step).

## Root Cause

The task-executor's commit step uses `git add` on specific files or directories named in the task description. For the frontend tasks, the commit messages referenced the components being built (e.g. `Build CategoryList + SubcategoryList + CategoriesPage + /categories route + nav links`) but the actual `git add` command apparently targeted already-tracked files or a narrower path glob, leaving the new page directories untracked.

The most likely failure mode: the executor ran `git add` on files it had modified (e.g. `frontend/src/App.tsx`, route config, `package.json`) but did not explicitly add the newly created directories, since those were not yet tracked and `git add <specific-file>` does not pick up sibling new files.

The `chore(category-management): mark plan complete` final commit was created without a `git status` check — so the untracked files were not caught before the PR was opened.

## Detection

Caught manually during a morning status review when `git status` showed `?? frontend/src/pages/categories/` and `?? frontend/src/pages/transactions/` alongside an open, "mergeable" PR. The PR title (`chore: mark plan complete`) was also a signal that the final commit was administrative, not feature code.

## Resolution

```bash
git add frontend/src/pages/categories/ frontend/src/pages/transactions/
git commit -m "feat(category-management): commit untracked frontend pages for categories and transactions"

git add specs/category-management/overview.md specs/category-management/erd.html
git commit -m "docs(category-management): add feature overview spec and ERD"

git push
```

Both commits were pushed to `feat/category-management` and are now included in PR #80.

## Lessons Learned

1. **`git add <specific-files>` does not pick up new sibling directories** — when a task creates new directories, the executor must explicitly add those paths or use `git add -A` scoped to the feature area.
2. **The final "mark plan complete" commit is a risk point** — it signals the executor considers work done but contains no code, making it easy to ship an incomplete PR.
3. **Spec/docs files are critical, not disposable** — `overview.md` and `erd.html` are the decision record for the feature and must be committed alongside the code.

## Prevention

1. The task-executor should run `git status` before each commit and warn (or fail) if untracked files exist in the working directory that match the feature area.
2. The plan-complete task should include an explicit `git status` check as a precondition, refusing to mark done if untracked files remain.
3. When writing tasks, include explicit `git add <new-directory>/` steps for any task that creates new files/directories from scratch.
4. Spec files generated by `/compass:plan` should be staged as part of the first task-executor commit (alongside the migration/schema task), not left to be picked up later.
