arc42 §1 Introduction & Goals

ShopKit — e-commerce platform

A full-stack e-commerce platform for independent retailers. Customers browse products, manage carts, and checkout with Stripe. Retailers manage inventory, view orders, and configure shipping through an admin panel. Built on React + Node.js + PostgreSQL, deployed to Azure.

Quality Goals

# Goal Measurable scenario
1Checkout reliabilityZero lost orders during checkout — Stripe webhook idempotency enforced
2Page performanceProduct listing page < 1.5s LCP on 4G connection
3Payment securityNo card data touches our servers — Stripe Elements only
4No duplicate constructsRegistry checked before every new construct is created

§4 Solution Strategy

# Decision Rationale
1Stripe Elements for paymentNo card data on our servers — PCI compliance without SAQ-D overhead. See ADR-002.
2JWT auth, stateless APIHorizontal scaling without sticky sessions. See ADR-003.
3Webhook queue for Stripe eventsIdempotent processing prevents duplicate order state changes. See ADR-005.
4Soft delete everywhere except sessionsOrders, products, users never hard-deleted — audit trail required. See ADR-001.
5Azure CDN for product imagesImages served from edge, not origin. Blob storage for uploads. See ADR-007.

arc42 §8 Crosscutting Concepts

§8 Crosscutting Concepts

Rules that apply uniformly across all building blocks. Deviation requires an ADR.

Soft Delete
All entities use deletedAt DateTime?. Hard deletes never used except sessions (see ADR-004). All queries filter WHERE deletedAt IS NULL. Applies to: orders, products, users, categories, carts.
ADR-001 →
JWT Stateless Auth
UserAuthService is the single point of token validation. AuthMiddleware attaches UserContext to every protected request. No session store. Refresh tokens are 30-day, JWT is 15-min.
ADR-003 →
Repository Pattern
Controllers and services never import Prisma directly. All persistence goes through a Repository. Repositories are the only constructs that touch Prisma client. Services call repositories.
ADR-006 →
API Response Envelope
All API responses: { data, error, meta }. Never naked arrays. Error: { code, message, details? }. Meta includes pagination. HTTP status codes must match error semantics.
ADR-008 →
Idempotency Keys
All Stripe API calls include idempotency keys. All webhook processing deduplicates on Stripe event ID. Prevents duplicate charges and double-processing of payment events.
ADR-005 →

Anti-Patterns

✗ Do not call Prisma directly from controllers or services — use a Repository.
✗ Do not format prices inline — always use formatCurrency().
✗ Do not hard-delete orders, products, or users — soft-delete only.
✗ Do not call Stripe without an idempotency key.

§9 Architecture Decisions

Click any row to expand the full decision. NFRs live here — not on individual constructs.

ADR-001
2026-01-10
Soft-delete strategy for all business entities
Accepted
E-commerce data has audit and dispute requirements. Orders in particular must never be deleted — regulatory requirement in AU/UK for 7 years. At decision time: 2 engineers, pre-launch, no specific compliance framework mandated yet.
We will use soft-delete (deletedAt timestamp) for all business entities. Hard deletes are prohibited except for session tokens.
OptionProsConsWhy rejected
Soft delete ✓Full audit trail, recoverable, dispute-safeQueries need deletedAt IS NULL everywhere; slightly more complex— chosen
Hard deleteSimpler queries, smaller tablesNo audit trail, irrecoverable, compliance riskCompliance risk. Orders must be retained.
Archive tableClean active tablesComplex migrations, two schemas to maintainOver-engineered for current scale.
Revisit if: a specific jurisdiction requires full data erasure (GDPR right-to-erasure for user data — handle via anonymisation, not hard delete).
ADR-003
2026-01-14
JWT stateless auth over server-side sessions
Accepted
We need auth for the storefront and admin panel. At decision time: 2 engineers, Azure Container Apps deployment (horizontally scalable), no Redis provisioned, 3-week MVP deadline.
We will use stateless JWT (15-min access token + 30-day refresh token). No server-side session storage.
OptionProsConsWhy rejected
JWT stateless ✓Stateless, horizontal scale, no Redis dependencyToken revocation requires blacklist; larger cookie— chosen
Server-side sessions + RedisEasy revocation, smaller tokenAdds Redis, sticky sessions or Redis Cluster neededAdds Redis dependency. Over-engineered at current scale.
NextAuth / ClerkManaged, feature-richVendor dependency, harder to customiseWanted full control. Vendor lock-in concern.
Revisit if: we need real-time session revocation (e.g. compromised account), or if team grows and manages auth becomes complex.
ADR-005
2026-02-03
Webhook queue (Service Bus) for Stripe event processing
Accepted
Stripe webhooks must be processed exactly once. A duplicate payment.succeeded event could result in double-fulfilling an order. At decision time: 50 orders/day in staging, Azure stack, webhook failures in testing when processing was synchronous.
We will use Azure Service Bus Standard queue to buffer Stripe webhook events with deduplication via Stripe event ID.
OptionProsConsWhy rejected
Service Bus queue ✓At-least-once delivery, dedup, retry, dead-letterExtra infra cost, adds latency— chosen
Synchronous processingSimple, low latencyStripe requires 200ms response; complex logic exceeds thisHit this in testing — Stripe retried, caused duplicates.
DB-backed queueNo extra infraPolling, DB load, build-your-own reliabilityWheel reinvention. Service Bus is the right tool.
Revisit if: order volume exceeds 50,000/day and we need premium tier SB features (sessions, transactions).
ADR-006
2026-01-12
Repository pattern — no direct Prisma in services
Accepted
Two engineers, both touching the same data access layer. Early decision to prevent query duplication and make future DB migrations testable. Observed in an earlier project that services importing Prisma directly made testing and refactoring painful.
All persistence goes through Repository classes. Services and controllers never import Prisma client directly.
OptionProsConsWhy rejected
Repository pattern ✓Single place for queries, testable, swappable ORMMore files, some boilerplate— chosen
Prisma directly in servicesLess boilerplate, fewer filesQueries scattered, hard to test services in isolationBurned by this previously — duplicated queries and untestable services.
Revisit if: switching ORMs — repositories abstract the ORM, so the blast radius is contained to repository files only.
