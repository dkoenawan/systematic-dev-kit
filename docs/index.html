arc42 §1 Introduction & Goals

§1 Introduction & Goals

compass-labs is a Claude Code plugin that provides opinionated, agent-driven skills for building production-ready full-stack applications — from blank repo to running product. It encodes best practices as executable /compass:<skill> commands covering project scaffolding, feature planning, codebase investigation, decision capture, and documentation maintenance.

Quality Goals

PriorityGoalMeasurable scenario
1No duplicate constructsAgent checks registry before creating any construct — 100% of the time
2Token efficiencyDuplicate check costs ≤ 2 file reads regardless of codebase size
3Decision preservationEvery significant decision captured in ADR at moment of decision — not reconstructed
4Spec-code fidelityEvery construct has a verified FR status or a diverged ADR — nothing silently drifts
5Human navigabilityDeveloper can answer any system question in ≤ 2 reads without opening source code

arc42 §4 Solution Strategy

§4 Solution Strategy

The 5 fundamental decisions that shape everything else.

#DecisionRationale
1 Construct registry over feature docs Feature specs capture intent at a point in time. Constructs persist. Indexing by capability (what it does) enables duplicate prevention that feature-level docs cannot.
2 arc42 as documentation spine, C4 as visual notation arc42 provides the 7 questions every system doc must answer. C4 fills the visual gap inside §5 (building block view). Together they give both structure and clarity.
3 Markdown source, HTML rendered view Markdown is git-diffable and agent-readable. HTML is human-navigable and visually rich. They are the same content in two formats. Neither is optional.
4 Every skill reads before acting, writes after acting The registry is a shared contract, not a side-car maintained by one skill. All skills are participants. doc-maintainer is the consistency guardian, not the sole writer.
5 Planned → Built → Verified → Diverged lifecycle The gap between spec and implementation is the failure mode. The lifecycle makes that gap visible and forces decisions to be recorded at the moment of divergence.
arc42 §5 Building Block View

§5 Building Block View

How the system is structurally decomposed — static view. Uses arc42's black box / white box model across three levels. Read only as deep as your task requires.

L0 Black box
docs/registry/index.md — hard limit 80 lines
Construct table with a "Does" column — one-line capability per construct. Feature Cross-Reference table. Known Gaps list. This is the capability search surface. Everything is a black box here — you see what it does, not how.
Stop here if you find what you need in the "Does" column, or confirm it doesn't exist.
L1 White box
docs/registry/constructs/<Name>.md — one file per construct
Full interface, FR list with proof status, dependency graph (calls / called-by), linked ADRs, patterns applied, status (planned/built/verified/diverged). This is the white box — you see how it connects externally. Still not the internals.
Stop here for planning, dependency tracing, or FR verification. Do not open source unless modifying internals.
L2 Source
src/... — the actual source file
The implementation. Read only when modifying internals, debugging, or verifying that implementation matches the L1 construct file. Not documentation — this is the code itself.
Stop here. There is no deeper level in the documentation system.
arc42 Level 1 sufficiency principle: "The Level 1 building block view is often sufficient for most stakeholders." In our terms: L0 and L1 answer most questions. L2 (source) is for implementation only.

arc42 §8 Crosscutting Concepts

§8 Crosscutting Concepts

Patterns and rules that apply uniformly across all building blocks. Before implementing anything, check if a pattern applies. Deviation requires an ADR.

Soft Delete
All entities use soft-delete (deletedAt DateTime?). Hard deletes are never used except for session tokens (see ADR-005). Queries always filter WHERE deletedAt IS NULL unless explicitly retrieving deleted records.
Implements: User, Order, Product, Notification · ADR-002
Authentication — JWT Stateless
All authentication uses stateless JWT tokens. No server-side session storage. UserAuthService is the single point of token validation. AuthMiddleware attaches UserContext to every protected request.
Implements: UserAuthService, AuthMiddleware, LoginPage · ADR-003
API Response Envelope
All API responses use { data, error, meta }. Never return naked arrays or raw model objects. Error shape: { code, message, details? }. Meta includes pagination when applicable.
Implements: all controllers · ADR-004
Repository Pattern
Controllers never call the database directly. All persistence goes through a Repository. Repositories are the only constructs that import Prisma client. Services call repositories, not Prisma.
Implements: all repositories · ADR-006

Anti-Patterns

Do not store auth state in React component state — use the auth context hook.
Do not call Prisma directly from controllers or services — always go through a Repository.
Do not return raw Prisma model objects from API routes — always map to a response DTO.
Do not use any type in TypeScript — use unknown + type guards.

§9 Architecture Decisions

Significant trade-off decisions with full options tables. NFRs are captured here, not on individual constructs. Before changing an approach, check if an ADR exists.

ADR-007 Accepted · 2026-03-14 Azure Functions over Service Bus for order → notification bridge
Context: We need to bridge the Order service and Notification service. At decision time: 2 engineers, < 500 orders/day, Azure-only stack, no compliance requirement for message durability, 3-week deadline to MVP.
We will use Azure Functions with HTTP triggers to bridge Order → Notification.
OptionProsConsWhy rejected
Azure Functions HTTP ✓ Simple, cheap at low volume, no infra to provision No guaranteed delivery, coupling if Notification is down — chosen
Azure Service Bus Guaranteed delivery, decoupled, scales to high volume Extra infra, cost, operational complexity for 2-engineer team Over-engineered for current scale. Adds SB management overhead with no benefit at < 500/day.
Direct DB polling No new services Polling latency, DB load, anti-pattern Anti-pattern — rejected immediately.
order volume exceeds 5,000/day, or if we need guaranteed delivery SLA for regulatory compliance.

Sufficiency Gates

The gate is the decision point: do I have enough context, or do I go deeper? arc42's level-1 sufficiency principle made explicit and operational per task.

Your task / question Start here Gate — stop if Go deeper to
"Does X already exist?" L0 "Does" column Found a match or confirmed absent Construct file for detail
"What does auth touch?" L0 Feature Cross-Ref Have the full construct list Individual construct files
"How does X work?" L0 → construct file Have interface + dependencies Source file (L2) for internals
"Why was X built this way?" decisions/index.md Found the ADR title Read the full ADR
"I'm modifying X — what breaks?" Construct file "Called by" Have the full caller list §6 runtime scenario for X
